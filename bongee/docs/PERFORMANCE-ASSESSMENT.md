# Bongee MCP 성능·수준 평가

최신 점검: [v0.4.1 기능 감사·성능 보완](AUDIT-v0.4.1.md). 아래는 이전 측정 이력입니다.

측정: 2026-10-08, 후속 장애 진단: 2026-10-09.

## 판정

현재는 **실사용 초기 단계**다. 전체 기능의 완전한 실행 동등성이나 운영 안정성이 검증된 완성품으로 평가할 수 없다. 도구 등록 범위는 넓지만 원격 호출 지연과 실제 자동 개발 중단이 확인됐다.

## 실측

동일 PC에서 SDK로 로컬 stdio와 공개 HTTPS MCP를 호출했다. 각 경로에서 목록 10회, `system_status` 순차 10회, 동시 5개씩 3회 호출했다. 모델 생성 시간을 포함하지 않는 읽기 전용 호출이다. 지연은 중앙값이며 p95는 작은 표본의 관측값이다.

| 항목 | 로컬 | 원격 HTTPS |
|---|---:|---:|
| 최초 연결 1회 | 1,563ms | 632ms |
| 도구 목록 중앙값 | 5.95ms | 303ms |
| 상태 조회 중앙값 | 1.84ms | 5,924ms |
| 상태 조회 p95 | 14.89ms | 6,822ms |
| 동시 5개 상태 조회 중앙값 | 3.99ms | 12,933ms |
| 동시 5개 상태 조회 p95 | 6.94ms | 19,947ms |
| 요청 성공 | 35/35 | 35/35 |

원격 실행기는 2초 간격으로 heartbeat·claim·report를 순차 수행하며 실행 슬롯이 제한된다. 이 전달 구조는 관측된 지연의 개선 후보다. 현재 표본으로 최대 처리량·장시간 안정성·다수 사용자 SLA를 확정할 수 없다.

## 기능과 자동화

- 로컬 418개, 원격 425개 도구를 확인했다. BATON 연결이 차단된 격리 환경에서는 로컬 373개였다. 네트워크 상태에 따라 사용 가능한 도구가 달라진다.
- 원본 Ruflo 358개 이름·입력 스키마 누락 0개, 변경 0개. 이 비교는 동작·성능 동등성 검증이 아니다.
- 기존 자동 추첨 모듈 검증 기록에는 실제 7역할, 1회 실패 후 수정, 8개 테스트 통과가 있다. 현재 모든 제품 작업에 대한 성공률로 일반화하지 않는다.
- 실제 사용자 파이프라인은 첫 기획 단계에서 Codex 101로 두 번 실패했다. 후속 복구에서도 런타임 panic을 확인했다. 단순 연결 성공·로그인 상태가 자동 작업 성공을 보장하지 않는다.
- 직접 Codex 실행에서는 일반 출력, JSON 스키마 출력, 원래 기획 입력이 정상 종료됐다. 실행기 경로와의 차이를 추가 진단한다. 같은 입력을 감독 프로세스로 실행해 `failed printing to stdout: Resource temporarily unavailable (os error 35)` panic을 재현했다. 감독 프로세스의 비차단 출력 fd를 Codex에 상속한 것이 원인이었다. 전용 child pipe와 스트림 역압 처리로 변경한 뒤 동일 입력이 종료 코드 0으로 완료됐다.

## 적용한 보완

- 승인된 개발 요청을 자동 파이프라인으로 시작·추적하도록 MCP 지침 보완.
- 단계별 일반 진행 확인을 반복하지 않도록 역할 지침 보완. 필수 권한 승인은 유지.
- 실패 종료 코드와 고정된 오류 종류를 표시하며 민감할 수 있는 stderr 원문은 영구 기록하지 않음.
- 읽기 전용 Codex 역할의 101 오류는 한 번 자동 재시도하고 실패 이력을 보존. 반복 실패는 중단하며 이미 파일을 썼을 수 있는 개발 역할은 무작정 재실행하지 않음.
- 수정 후 자동 회귀 112개 통과(4 MB 동기 출력 회귀 포함). 실제 사용자 파이프라인의 완료와는 별개다.

근거: `output/level-assessment/results.json`, `docs/catalog-parity.json`, `docs/PIPELINE-VERIFICATION.json`, 실제 비공개 실행 기록.

구조화된 결과와 실제 검증 명령의 분리는 [OpenAI의 Codex 반복 복구 예제](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)도 참고했다. 이 문서는 외부 벤치마크 순위나 임의의 점수를 주장하지 않는다.

## 2026-10-09 완료 응답 전달 개선 · 로컬 검증

실행기에서 RPC 결과가 준비되면 다음 2초 폴링을 기다리지 않고 취소 여부를 확인한 뒤 즉시 보고한다. 주기 검사와 완료 콜백은 작업별 보고 요청을 공유하여 중복 보고를 막는다. 보고 실패 시 결과를 보존해 다음 주기에 재전송하며 도구를 다시 실행하지 않는다.

서버가 완료 결과를 받았지만 HTTP 응답만 유실된 경우, 완료 시 lease를 삭제하던 기존 동작 때문에 재전송이 계속 409로 거절되고 실행기 슬롯이 남았다. 완료 작업의 비공개 lease를 보존해 같은 lease의 재전송을 확인하며 최초 결과는 변경하지 않는다. 잘못된 lease는 계속 거절하고 목록·상태·결과에서 lease를 노출하지 않는다. 작업 기록의 기존 개수 제한을 유지한다.

동일 로컬 HTTP 게이트웨이에서 즉시 응답하는 모의 도구와 실제 2초 폴링 간격으로 각 3회 측정했다. 큐에 등록한 뒤 곧바로 claim하는 통제 조건이며 WAN·모델 생성·유휴 상태의 큐 발견 시간은 제외한다.

| 완료 응답 전달 경로 | 중앙값 | 관측값 3회 |
|---|---:|---|
| 수정 전 실행기 (`ecbde05`) | 2,020.47ms | 2,020.47 / 2,018.50 / 2,020.97ms |
| 수정 후 실행기 | 101.02ms | 101.57 / 101.02 / 100.74ms |

근거: `output/rpc-delivery/measure.mjs`, `output/rpc-delivery/results.json`. 결과 JSON에 기준 커밋과 양쪽 실행기 및 게이트웨이의 SHA256을 기록했다. 공개 HTTPS 속도 개선 수치로 일반화하지 않는다. 큐 발견의 2초 간격, 전체 카탈로그 heartbeat 전송, 실행 슬롯 제한은 남아 있다.

검증: 전체 자동 테스트 117개 통과. 관련 HTTP·실행기 검사 12개에는 즉시 보고, 취소 경쟁, 통신 실패 후 재시도, 서버 접수 후 응답 유실, 도구 중복 실행 방지, 잘못된 lease 거절, lease 비공개 검사가 포함된다. 변경은 로컬 소스에 적용됐으며 공개 서버 배포와 사용 중 실행기 교체는 수행하지 않았다.
